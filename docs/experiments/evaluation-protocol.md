# Evaluation Protocol

Status: proposed comparison protocol with an implemented single-method scenario runner. The allocation tests and fixed scenario checks assess software behavior and feasibility; they do not establish superiority over another method.

## Available Scenario Runner

Run `python scripts/evaluation/run_allocation_scenarios.py` from the repository root to produce a Markdown table, or add `--format json` for per-location allocations, unmet demand, total service, unused budget, and the maximum constraint violation. The runner uses only the Python standard library and resolves its default fixture independently of the working directory.

The [versioned fixture](../../configs/optimization/allocation-scenarios.json) has `schema_version: 1` and a nonempty `scenarios` list. Each entry contains a unique lowercase `id` (letters, digits, underscores, or hyphens), equal-length nonempty numeric `demand` and `capacity` lists, and a numeric `budget`. Values must be finite and non-negative; booleans and numeric strings are rejected. All quantities use the same divisible service-capacity unit for one period. Array positions identify corresponding generic locations. A zero capacity denotes a closed location, whose demand remains unmet.

Use `--scenarios path/to/scenarios.json` to evaluate another configuration. Entries run in file order; these fixed inputs require no random seed. The output reports the method, schema version, and absolute feasibility tolerance of `1e-9` service-capacity units. It checks non-negative allocation, local capacity, requested demand, and the shared budget. A report containing an infeasible allocation exits with status 1; invalid input exits with status 2. Values displayed in the table are rounded to two decimal places; feasibility uses unrounded values.

The five supplied scenarios are regression fixtures, not a representative demand sample or an evaluation of a constrained optimizer. Comparative experiments, stochastic scenario generation, and the full reproducibility record below remain future work.

## 1. Experimental Contract

Before running a comparison, record the research question, primary metric, scenario distribution, units, interval length, forecast horizon, capacity definitions, and comparison methods. Freeze weights, tuning budgets, and failure-handling rules before inspecting test results.

Synthetic scenarios should include ordinary load, demand above capacity, uneven demand, zero demand, zero resource budget, closed locations, and demand shocks. Use generic location identifiers and explicitly synthetic values. Distinguish a fixed fixture from a sample generated by a seeded procedure.

## 2. Data Splits and Baselines

For time-dependent data, use chronological training, validation, and test partitions or rolling forecast origins. Fit preprocessing on training data, tune on validation data, and retain the final test interval for assessment. At each decision time, use only information that would have been available then. Separate known future schedules from realized future outcomes.

Use the same observation availability and evaluation scenarios for competing methods. Proposed comparisons include:

| Component | Reference methods | Main comparison |
|---|---|---|
| Forecasting | Last observation; seasonal naive where appropriate | Accuracy by horizon and location |
| Allocation | Existing proportional heuristic; planned constrained optimizer | Feasibility and common objective components |
| Pricing | Fixed, rule-based, and optimization-based policies | Realized revenue, congestion, unmet demand, and service measures |
| Recommendation | Preference-only and congestion-aware rankings | Ranking quality and destination effects |
| Language interface | Matched generation with and without retrieved evidence | Supported claims and consistency with structured decisions |

Use matched simulator assumptions for pricing comparisons, including demand response, admissions, and departures. Record training interactions and computational budgets separately from evaluation runtime.

## 3. Forecasting Metrics

For $N>0$ held-out targets $y_j$ and forecasts $\hat y_j$, define

$$
\operatorname{MAE}=\frac{1}{N}\sum_{j=1}^{N}|y_j-\hat y_j|,
\qquad
\operatorname{RMSE}=\sqrt{\frac{1}{N}\sum_{j=1}^{N}(y_j-\hat y_j)^2}.
$$

Report these by location and horizon, with the aggregation rule declared. For non-negative demand, percentage error may additionally be reported on $\mathcal P=\{j:y_j>0\}$:

$$
\operatorname{MAPE}_{+}=\frac{100}{|\mathcal P|}
\sum_{j\in\mathcal P}\left|\frac{y_j-\hat y_j}{y_j}\right|.
$$

Label this as positive-target MAPE and report the number of excluded zeros. It is undefined if $\mathcal P$ is empty and unstable for very small targets. Keep MAE and RMSE over all valid observations; do not silently substitute a small denominator. Definitions, percentage-error limitations, and temporal validation follow [Forecasting: Principles and Practice, Chapter 5](https://otexts.com/fpp3/toolbox.html#evaluating-point-forecast-accuracy).

For nominal $(1-\alpha)$ prediction intervals $[L_j,U_j]$, report empirical coverage and mean width:

$$
\operatorname{Coverage}=\frac{1}{N}\sum_j\mathbf 1\{L_j\leq y_j\leq U_j\},
\qquad
\operatorname{Width}=\frac{1}{N}\sum_j(U_j-L_j).
$$

Declare $0<\alpha<1$, check $L_j\leq U_j$, and evaluate by horizon. Interpret coverage together with width; very wide intervals can cover observations without providing useful precision.

## 4. Allocation and Policy Metrics

For non-negative scenario demand $d_{i,t}$ and assigned service $x_{i,t}$, define unmet demand $u_{i,t}=d_{i,t}-x_{i,t}$ under the constraint $x_{i,t}\leq d_{i,t}$. Report:

- Total service, total unmet demand, and priority-weighted unmet demand.
- Operating cost and changes in allocation between periods.
- Shared-budget residual and every capacity-constraint violation.
- Solver status, runtime, and optimality gap when applicable.
- Failure and timeout counts, using a stated fallback policy.

Compare the same objective, coefficients, and constraints across methods. With equal unmet-demand weights and zero operating and adjustment costs, the existing heuristic already maximizes total service in the simple single-period model. Under those assumptions, a new optimizer should not be described as improving total served demand. Heterogeneous priorities, costs, or temporal constraints create different comparison questions.

For pricing or adaptive policies, record discounted return alongside unweighted revenue, unmet demand, peak occupancy, admission rejections, and any declared satisfaction or environmental proxies. Distinguish arrival volume from occupancy. Report violation magnitudes as well as frequencies; penalty terms alone do not establish feasibility.

## 5. Recommendation and Language Evaluation

For visitor $u$, a list $L_u$ of $K$ distinct recommendations, and a held-out relevant set $T_u$, define

$$
\operatorname{Precision@K}=\frac{|L_u\cap T_u|}{K},
\qquad
\operatorname{Recall@K}=\frac{|L_u\cap T_u|}{|T_u|}.
$$

Require $K>0$ and declare the treatment of candidate sets smaller than $K$. Recall is undefined for an empty relevant set; report exclusion counts or a predefined convention. Relevance labels and the evaluation candidate pool must be specified.

For non-negative relevance grades $g_{u,j}$ at rank $j$,

$$
\operatorname{DCG@K}=\sum_{j=1}^{K}\frac{2^{g_{u,j}}-1}{\log_2(j+1)},
\qquad
\operatorname{NDCG@K}=\frac{\operatorname{DCG@K}}{\operatorname{IDCG@K}}.
$$

IDCG uses the ideal ranking from the same evaluation candidate pool. State the zero-IDCG convention and aggregation over visitors. Evaluate exposure across locations and simulated congestion separately: offline ranking accuracy does not establish visitor redistribution or a causal improvement in satisfaction.

For the language interface, freeze a query set, knowledge snapshot, and structured decision inputs. Assess retrieved evidence relevance, supported factual claims, citation correctness, multilingual consistency, abstention on insufficient evidence, and agreement with numerical outputs. Report human-rating criteria, sample size, and disagreements. A fluent explanation is not evidence that an allocation or price is correct.

## 6. Ablations and Statistical Reporting

Candidate ablations replace learned forecasts with a reference forecast, adaptive pricing with fixed pricing, congestion-aware ranking with preference-only ranking, or retrieved context with no retrieved context. Specify the replacement behavior so the remaining system remains operable. Evaluate sensing-source removal only once multiple sensing sources exist.

Run stochastic methods across multiple training seeds and independent evaluation scenarios; state both counts. Pair methods on shared scenario draws where appropriate, but do not treat correlated time steps from one trajectory as independent experimental replications. For dependent time series, use an uncertainty method that respects dependence and document its resampling unit.

Report means, dispersion, confidence intervals, and effect sizes for paired method differences. Specify interval construction, confidence level, hypothesis tests if used, and any multiple-comparison adjustment. Include unsuccessful runs and practical effect sizes, rather than selecting only favorable seeds or statistically significant metrics.

## 7. Reproducibility Record

Each future experiment should preserve:

- Code revision, method name, configuration, and data or scenario version.
- Training and evaluation seeds, split boundaries, horizon, and interval length.
- Metric definitions, units, normalization constants, and objective weights.
- Interpreter, library and solver versions, hardware, runtime, and solver tolerances.
- Machine-readable component metrics, constraint residuals, and run status.
- A summary that distinguishes synthetic evaluation, historical replay, and any later field evidence.
